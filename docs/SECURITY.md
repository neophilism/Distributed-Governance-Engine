# Security design and verification boundaries

Authoritative architecture is docs/ARCHITECTURE.md. Upstream: neophilism/End-To-End-Everywhere-Security-Architecture-Standard at d916938cb6b0e6569edfde88555984ddacb96021 (development, not certified release). Read spec/security-properties.md, spec/transport-security.md, spec/server-trust-minimization.md and spec/secure-development-standard.md from that pinned source when implementing their flows.

Design mappings: identity/device authorization → DCE-002/003/011; content confidentiality and group encryption → DCE-003/008; authorization integrity → DCE-010/011/018/028; document/ballot integrity → DCE-009/012/013/014/019/020; attachments/export disclosure → DCE-024/025/026/027; verification/transparency → DCE-021/022/023; secure development and supply chain → DCE-036; transport/server/operator/restore boundaries → DCE-035. These are subject-area mappings, not requirement-complete compliance evidence.

Required adversaries: compromised service/operator/database/backup, active client, malicious eligible participant, Sybil/ring, forged proxy/weight, cross-tenant actor, stale/duplicate replay, concurrent closer/adopter, malicious import, confused-deputy export, publication without consent, signer substitution, delayed/lying chain RPC, reorg, split log views and omission of acknowledged receipts. Endpoint compromise and recipient retention remain explicit limitations; no cryptography can remove old plaintext from a recipient.

Controls: minimize PII; ciphertext-only private payloads outside authorized endpoints; no server application decryption keys; explicit public disclosure; default-deny capabilities at every API/room/search/export/worker; immutable snapshots and digest binding; exact integers; uniqueness/idempotency; atomic commit/outbox; versioned invariant settings; sanitized/isolated imports; CSP and secure sessions; rate bounds; no content/ink/secret telemetry; tested encrypted backup/restore and key recovery. RLS supplements request authorization; no routine BYPASSRLS credentials. Application E2EE and TLS are distinct, and all transport termination points must be inventoried.

Actual foundation: pure functions and tests only. No private encryption protocol, device trust, authentication, RLS, persistent database transaction, immutable remote store, payment/signing/chain provider or network policy is implemented. SHA-256 digests/Merkle inclusion do not by themselves establish legal authority, honest voters, full event completeness or certification. Development canonicalization is restricted and versioned; do not ship it as an unreviewed permanent interoperability contract.

The user's October 16 direction and existing October 13 repository policy authorize AI-assisted source/security review and substantive tests without waiting for an external human audit, paid review or E2EESA certification. External review remains honestly pending for the final deployed handoff. Do not misrepresent author self-review as independent review or disable technical controls. Actual high-impact findings and failed required checks must be fixed.

security/e2eesa-status.json is compatible with the Engine Room parser. Every production stage is false/pending. Foundation tests are not full security testing. scripts/validate-security.mjs verifies that the foundation does not accidentally claim production assurance. Future implementation replaces that foundation-only guard with evidence verification, without marking review complete until it is real.
